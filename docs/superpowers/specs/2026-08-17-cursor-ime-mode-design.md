# cursor-ime-mode 設計仕様

作成日: 2026-08-17

## 1. 目的

Windows で文字を入力する前に IME の状態を確認したい。標準のタスクバー通知領域は視線移動が大きく、入力位置から遠い。本ツールは **テキストキャレットのすぐ横に IME の状態バッジを一瞬だけ表示**することで、視線を入力位置から動かさずに状態を確認できるようにする。

対象は全アプリケーション（OS 全体）。特定のエディタ拡張ではない。

## 2. 実現可能性の検証結果（実測済み）

設計に先立ち、使い捨ての検証スクリプトで以下を実測した。検証スクリプトは `docs/superpowers/specs/` 配下には残さず、回帰確認手順としてのみ §9 に記載する。

### 2.1 キャレット矩形の取得手段

| アプリ | `GetGUIThreadInfo` | **MSAA `OBJID_CARET`** | UIA `TextPattern` |
|---|---|---|---|
| メモ帳 (`RichEditD2DPT`) | ✅ 追従 | ✅ `1x15` 追従 | △ `1x31`（行高） |
| エクスプローラー（Win32 `Edit`、例: F2 名前変更）\*2 | ✅ | ✅ | ❌ 要素全体 |
| Edge (Chromium) | ❌ | ✅ `1x21` 打鍵ごとに追従 | △ 追従するが要素全体を返す場合あり (`548x40`) |
| VS Code (Electron) | ❌ | ✅ `1x19` 打鍵ごとに追従 | ❌ 行全体 `1663x19`、x 座標が固定 |
| Windows Terminal | ❌ | ❌ `(0,0)` | ✅ `9x19` |
| 非テキスト要素（デスクトップ、ボタン等）\*1 | ❌ | ❌ `(0,0)` | ❌ TextPattern なし |

**結論**: MSAA `OBJID_CARET` を主手段、UIA を補完手段とする。事前予想（Chromium 系は UIA が必要）は実測により覆された。

**この時点で立てた仮説（後日訂正）**: 非テキスト要素では MSAA が常に `(0,0)/0x0` を返すように見えたため、「文字入力可能な状態か」の判定を追加コストなしに得られると考えた。しかし後日の追加実測で、Chromium はフォーカスがテキスト要素から外れても直前のキャレット座標を破棄せず、位置はあるが面積だけが 0 の矩形を返すことが判明し、この仮説は誤りだったとわかった。この誤った前提が実装のバグの原因になっている。詳細と設計上の帰結は §6.1 を参照。

\*1 上表の行は初期実測時点の記録（デスクトップ、ボタンなどを対象とした計測）である。後日 Chromium 限定で追加実測したところ、フォーカスがツールバーボタン（`accFocus` role `PUSHBUTTON(0x2B)`）にある場合、MSAA は座標を保持したまま `(235,49) 0x20`（面積ゼロ）を返し、`(0,0)` にはならないことが判明した。また Web ページ本体（`role=DOCUMENT(0x0F)`）は UIA `TextPattern` に応答する（`textPattern=True`）ため、「TextPattern なし」もこのケースには当てはまらない。§6.1 を参照。

\*2 当初「エクスプローラー検索欄」とラベル付けしていたが、これは未検証のまま `focusCls=Edit` という観測結果から推測した誤りだった。後日の再測定（`proc=explorer`）で切り分けたところ、実際に MSAA 経由で動作するのは F2 名前変更などの古典的な Win32 `Edit` コントロールであり、Windows 11 の検索ボックスは XAML 化された `InputSiteWindowClass` で、MSAA `accFocus` role は `CLIENT(0x0A)`、`OBJID_CARET` は全ゼロ、UIA もキャレットを提供しないため、バッジは出ない。これは今回の `CaretLocator` 修正による退行ではない — 修正が変えたのは「位置はあるが面積ゼロ」の矩形の扱いのみであり、全ゼロ矩形の経路（検索ボックスがたどる経路）は変更されていない。

**未検証**: Chrome と Cursor は計測時に捕捉されなかった。いずれも Edge / VS Code と同じ `Chrome_WidgetWin_1` クラスの Chromium / Electron であり同等と**推論**するが、実測ではない。Slack / Discord / Teams は当該 PC に未インストールのため未検証。

### 2.2 IME 状態の取得

`ImmGetDefaultIMEWnd(hwnd)` で得た IME ウィンドウに対し、クロスプロセスで `WM_IME_CONTROL` (0x0283) を送る。

- `IMC_GETOPENSTATUS` (0x0005) → IME の ON/OFF
- `IMC_GETCONVERSIONMODE` (0x0001) → 変換モードのビットフラグ

全対象アプリで ON/OFF の切り替えが正しく読めることを確認済み。`ImmGetContext` / `ImmGetOpenStatus` はプロセス内専用のため使用できない。

### 2.3 変換モードのビット値

実測値（`open=1` の場合）:

| 実測 `conv` | 意味するビット | モード |
|---|---|---|
| `0x9` | NATIVE \| FULLSHAPE | ひらがな |
| `0x3` | NATIVE \| KATAKANA | 半角カタカナ |
| `0x8` | FULLSHAPE のみ | **全角英数** |

ビット定義: `NATIVE=0x1`, `KATAKANA=0x2`, `FULLSHAPE=0x8`, `ROMAN=0x10`。

`ROMAN` ビット (`0x10`) は独立に立つことがあり（エクスプローラーで `0x19` を観測）、モード判定には無関係なのでマスクで無視する。

`open=0` のとき `conv` の値は無意味（Edge で `0x9` と `0x0`、エクスプローラーで `0x19` と、スレッドごとにばらついた）。**必ず `open` を先に見る。**

### 2.4 オーバーレイのフォーカス保持

`WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW | WS_EX_TRANSPARENT` と `ShowWithoutActivation` の組み合わせで、**バッジ表示中のフォーカス奪取は 1 回も発生しなかった**（180 秒の計測で検出 0 件）。表示中も対象アプリの前面ウィンドウ判定と IME 読み取りが正常に継続することを確認済み。

これは重要な前提である。オーバーレイがフォーカスを奪うと、報告対象の IME 状態そのものが破壊され、かつ `GetForegroundWindow` が自分自身を返して読み取り経路全体が静かに壊れる。

## 3. 実装方式

- **言語 / フレームワーク**: C# + WinForms
- **ビルド**: Windows 標準搭載の `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`。.NET SDK も NuGet も不要。
- **成果物**: 単体 exe 1 つ + 設定ファイル
- **常駐形態**: タスクトレイアイコン常駐

**制約**: 同梱の `csc.exe` は C# 5 相当のため、文字列補間、式形式メンバー、`nameof`、`out var` は使用できない。

## 4. アーキテクチャ

Win32 依存部と純粋ロジックを分離する。純粋ロジックのみが自動テスト対象となる。

| コンポーネント | 責務 | 依存 |
|---|---|---|
| `ImeMode` (enum) | 6 状態の列挙 | なし |
| `ImeDecoder` | `open` / `conv` → `ImeMode`。**純粋関数** | なし |
| `ImeReader` | `WM_IME_CONTROL` による生値取得 | Win32 |
| `CaretLocator` | MSAA 主・UIA 従でキャレット矩形取得 | Win32 / COM |
| `FocusHook` | `EVENT_OBJECT_FOCUS` を購読しフォーカス移動を記録 | Win32 |
| `BadgeStateMachine` | 表示/非表示/移動と表示時間を決める。**純粋** | なし |
| `InputContextWatcher` | ポーリングで 1 サンプル収集し、状態機械を駆動してイベント化 | 上記 |
| `BadgePlacer` | キャレット矩形＋画面情報 → バッジ座標。**純粋関数** | なし |
| `BadgeWindow` | `NOACTIVATE` レイヤード窓の描画とフェードアニメーション | WinForms |
| `TrayApp` | NotifyIcon、設定読込、多重起動防止、寿命管理 | 全部 |

## 5. データフロー

```
EVENT_OBJECT_FOCUS ─→ FocusHook がフラグを立てる（非同期）

120ms タイマー
  ├→ GetForegroundWindow()
  ├→ GUITHREADINFO.hwndFocus でフォーカスウィンドウを特定
  ├→ CaretLocator.TryGetCaret(hwndFocus)     ┐
  ├→ ImeReader.Read(hwndFocus)               ├→ Sample
  └→ FocusHook のフラグを消費                 ┘  { hasCaret, rect, mode, focusChanged }
        ↓ BadgeStateMachine.Next(sample, now)
     caret 無 → 有        ⇒ 入力可能になった   → バッジ表示
     mode 変化             ⇒ 状態が変わった     → バッジ表示（表示時刻をリセット）
     focusChanged          ⇒ 別の入力欄に移った → バッジ表示（表示時刻をリセット）
     caret が 2px 以上移動 ⇒ 入力が始まった     → フェードアウト
     表示から 800ms 経過   ⇒ 役目を終えた       → フェードアウト
     caret 有 → 無        ⇒ 入力不可になった   → 即座に隠す（フェードなし）
```

**表示時間の管理は状態機械側に置く。** `BadgeWindow` に持たせるとフェード完了が状態機械に伝わらず、内部の「表示中」フラグが実体とずれて以後の表示判定が全て狂う。`BadgeWindow` は描画とフェードアニメーションだけを担当する。

### 5.1 表示・非表示の規則

**表示するトリガー（いずれか）**

1. 入力可能なコントロールにフォーカスが移った
2. IME モードが変化した

トリガー 1 は**キャレットの有無の変化だけでは検知できない**。同じウィンドウ内で別の入力欄をクリックした場合、キャレットは一度も消えないため「移動した＝入力が始まった」と誤判定され、バッジが出なくなる。しかも実測ログでは Edge のアドレスバーもページ内の入力欄も `focusCls=Chrome_WidgetWin_1` で同一なので、フォーカスウィンドウ (HWND) の比較でも解決しない。要素単位で発火する `SetWinEventHook(EVENT_OBJECT_FOCUS)` を使う。

**未検証**: Chromium 系アプリが同一ウィンドウ内の入力欄移動で `EVENT_OBJECT_FOCUS` を発火するかは実装時に実測して確定する。発火しない場合は、その組み合わせを既知の制約として README に明記し、推測による代替手段は足さない。

**隠すトリガー（早い者勝ち）**

1. 表示から 800ms 経過（フェードアウト 200ms）
2. キャレットが 2px 以上移動した（＝入力またはカーソル移動が始まった。フェードアウト 200ms）。ただし組み立てた位置（6.2 の空の入力欄フォールバックによる合成矩形）はこの判定の対象外とする — 理由と挙動の詳細は次段落。
3. 入力可能な状態でなくなった（即座、フェードなし）

**設計意図**: 要件は「入力**前**の確認」である。入力が始まった時点でバッジは役目を終えているため消す。キャレット移動を入力開始の合図とするのは、グローバルキーボードフックが常駐アプリとして重くセキュリティソフトの誤検知を招きやすい一方、キャレット座標は既に取得済みで追加コストがゼロだからである。矢印キーやマウスクリックによる移動も拾えるが、いずれも「ユーザーが既に操作を始めた」ことを意味するので目的に適う。

2px の閾値は誤検出を防ぐためのもの。検証時、待機中のキャレット座標は完全に静止していた（メモ帳で `(119,114)` が固定）。

移動量の基準点は**バッジを表示した時点のキャレット座標**とする。フォーカス移動やモード変化で表示した直後に、その表示自体が移動と判定されて即座に消える事故を防ぐため。バッジが非表示のあいだキャレットが移動しても何も起こらない。

**組み立てた位置（6.2 の空の入力欄フォールバック）は、この基準点による再アンカーも移動判定との比較も行わない。** 要素の `BoundingRectangle` はレイアウトの再計算やアニメーションで動くのであって、ユーザーが入力やカーソル移動を始めたことを意味しないためである。実測（メモ帳の検索バー）ではユーザーが何も操作していないのに、要素矩形が 120ms のポーリング間隔のあいだに最大 95px 動いた。この揺れに 2px 閾値の移動判定を適用すると表示直後にフェードアウトしてしまうため、`BadgeStateMachine.Next` は組み立てた位置に対しては移動判定そのものをスキップし、位置を最初に表示された場所へ固定したまま `Move` ではなく `None` を返す（表示から `ShowDurationMs` 経過した場合のフェードアウトと、IME モード変化による再表示は通常どおり働く）。

**競合の解決**: 未確定文字の変換中に IME モードを切り替えると、モード変化（表示）とキャレット移動（非表示）が同じサンプルで発生しうる。この場合は**モード変化を優先**して表示し、次のサンプル以降のキャレット移動で隠す。

**意図的に採用しないこと**: 「手が止まったら再表示」は実装しない。入力中に何度も出入りすると邪魔になり、入力前の確認という目的から外れる。

## 6. キャレット取得の詳細

### 6.1 主手段: MSAA

```
AccessibleObjectFromWindow(hwndFocus, OBJID_CARET(0xFFFFFFF8), IID_IAccessible, out acc)
  → IAccessible.accLocation(out x, out y, out w, out h, CHILDID_SELF)
```

MSAA の応答は 3 分岐で扱う（`CaretLocator.ChooseCaret` に実装、純粋関数として単体テスト済み）。

| MSAA の応答 | 意味 | 動作 |
|---|---|---|
| `hr != 0` / 例外 / 全て 0 | 判断材料が無い | UIA に問い直す |
| **位置はあるが妥当性ガード（6.2 の `IsPlausibleCaret`）を通らない矩形**（面積が無い、または幅が高さの4倍を超えるなど） | **「キャレットはあるがテキスト欄ではない」** | **UIA も見ずにキャレット無しとする** |
| 妥当な矩形（6.2 の妥当性ガードを通過） | 本物のキャレット | 採用 |

**根拠（実測）**: Chromium は入力欄以外へフォーカスが移っても、エミュレートしたシステムキャレットを破棄しない。Edge のアドレスバーから Tab でツールバーのボタンへ移動すると、MSAA `OBJID_CARET` は座標 `(235,49)` を保持したまま幅だけ `1→0` になる（`accFocus` の role は `PUSHBUTTON(0x2B)`）。30 秒間の継続入力計測では、編集可能な欄で幅が 0 になったことは一度もなく（常に 1 以上）、幅 0 は非テキストフォーカス時にのみ観測された。

この分岐の 2 番目で **UIA に問い合わせてはならない**。Web ページ本体（`DOCUMENT` role）は `TextPattern` を持つため UIA が応答してしまい、ページ本体の位置に新しいバッジを出す不具合を生む。さらに Edge の UIA は同じ入力欄に対して MSAA と約 150px ずれた X 座標を返すことも実測されている（MSAA `X=265〜375` に対し UIA `X=108/128`）。したがって「UIA にフォールバックしてから妥当性で弾く」という単純な統一処理では対応できず、MSAA が位置情報を返した時点で UIA を呼ばないことが必須である。

### 6.2 補完手段: UIA

`AutomationElement.FocusedElement` から `TextPattern` を取得し、`GetSelection()[0]` の `GetBoundingRectangles()` を使う。選択が折りたたまれていて矩形が空の場合は、範囲を 1 文字分広げてから再取得する（それでも矩形が得られない場合の例外は後述）。UIA は **MSAA が判断材料を返さなかった場合にのみ**呼ぶ（6.1 参照）。

**妥当性ガード（必須）**: `IsPlausibleCaret` は MSAA・UIA いずれの結果にも適用する共通の判定であり、`ChooseCaret` から一元的に呼ばれる。UIA が返す矩形はキャレットではなく行全体や要素全体であることがある（VS Code で `1663x19`、Edge で `548x40` を観測）。そのまま使うとバッジが行頭に飛ぶ。

> **幅が高さの 4 倍を超える矩形、または幅・高さのいずれかが 0 以下の矩形はキャレットとみなさず棄却する。**

この閾値は Windows Terminal の `9x19` とメモ帳の `1x31` を通し、VS Code の `1663x19` と Edge の `548x40`、および幅 0 の Chromium 非テキストフォーカス（`235,49,0,20`）を弾く。

棄却された場合は**何も表示しない**。位置を推測して表示することはしない。誤った位置に出すくらいなら出さないほうが良い。

**例外（空の入力欄への限定的なフォールバック）**: ただし一点だけ、上記の原則に限定的な例外を設ける。`TextPattern` の `GetSelection()[0].GetBoundingRectangles()` が矩形を一切返さず（1 文字分広げての再取得も空のまま）、かつフォーカス要素の `ControlType` が `Edit` である場合に限り、要素自身の `BoundingRectangle` の左端を幅 1px・高さは要素と同じの矩形としてキャレット位置に採用する（`CaretLocator.TryEmptyFieldCaret`、純粋関数として単体テスト済み）。

理由: 空の入力欄にフォーカスした瞬間こそ「文字を入力する前に IME を確認する」という本ツールの目的の核心である。ここでバッジが出なければ、まさに確認したい瞬間に確認できないことになる。実測（メモ帳 `Ctrl+F` 検索ボックス、`focusCls=InputSiteWindowClass`、XAML/WinUI 製）: `ControlType=Edit`、`TextPattern=True` は空でも 1 文字入力後でも変わらないが、UIA キャレット矩形は空のとき `EMPTY(no bounding rects)`、1 文字入力後は `(207,110) 34x19` となる。MSAA は常に全ゼロなので UIA が担当するが、UIA は文字が 1 つも無いキャレットの矩形を返せない。

適用条件を `ControlType.Edit` に厳格に限定することが、この例外の安全性の核心である。Web ページ本体は `ControlType.Document` かつ `TextPattern=True` でありながら選択範囲を持たない（Edge で実測: `role=DOCUMENT(0x0F)`, `textPattern=True`）。もしこの処理を `ControlType` を問わず適用すると、ページ全体の `BoundingRectangle` にバッジを出してしまう — これは直前に修正した「Chromium で古いキャレット位置にバッジが残り続ける」不具合（本節冒頭）の変種である。したがって `Document` を含め `Edit` 以外の `ControlType` はすべてこの経路で拒否する（`TryEmptyFieldCaret` の `isEditControl` ガード）。なお、エクスプローラーの検索ボックスは `ControlType.Pane` であり UIA がそもそも `TextPattern` に応答しないため、この例外の対象にすらならない。

この例外は `TextPattern` が矩形を一切返せなかった場合の最後の手段としてのみ働く。`TextPattern` が矩形を返した場合（本節冒頭の経路）の動作は変更しない。

### 6.3 入力可能性の判定

MSAA と UIA の双方が有効な矩形を返さなかった場合、その時点で「文字入力可能な状態ではない」と判定する。専用の判定ロジックは設けない。なお、MSAA が「位置はあるが妥当性ガードを通らない」矩形を返した場合（§6.1）は UIA を意図的に呼ばないため、UIA が実際には有効な矩形を返せたかどうかに関わらずその時点で判定が確定する。

## 7. バッジの表示仕様

| `ImeMode` | 表示文字 | 色 |
|---|---|---|
| `Hiragana` | あ | 緑 |
| `FullKatakana` | ア | 緑 |
| `HalfKatakana` | ｱ | 緑 |
| `FullAlnum` | Ａ | 青 |
| `HalfAlnum` | A | 青 |
| `Off` | A | グレー |

`HalfAlnum` と `Off` は表示文字が同一のため、**色で区別する**。

### 7.1 ウィンドウスタイル

```
WS_EX_NOACTIVATE  (0x08000000)  フォーカスを奪わない（必須）
WS_EX_TOOLWINDOW  (0x00000080)  Alt+Tab に出さない
WS_EX_TRANSPARENT (0x00000020)  クリック貫通
WS_EX_LAYERED     (0x00080000)  下記参照
```

加えて `ShowWithoutActivation => true`、`TopMost = true`、`ShowInTaskbar = false`、`FormBorderStyle = None`。

**不透明度**: 設定ファイルで 0.1〜1.0 の範囲で調整可能とする（既定 0.88）。

**注意**: クリック貫通（`WS_EX_TRANSPARENT`）はレイヤードウィンドウであることが前提である。WinForms は `Opacity < 1.0` のとき自動的に `WS_EX_LAYERED` を立てるが、**不透明度を 1.0 に設定した場合は明示的に `WS_EX_LAYERED` を立てる必要がある**。

### 7.2 配置

既定はキャレット矩形の右上（`x + 6`, `y - バッジ高 - 4`）。

`BadgePlacer` は対象モニタの作業領域を受け取り、はみ出す場合は反転する:

- 右にはみ出す → キャレットの左側に出す
- 上にはみ出す → キャレットの下側に出す

マルチモニタでは、キャレット座標を含むモニタの作業領域を基準にする。

### 7.3 DPI

`app.manifest` で PerMonitor V2 を宣言し、`csc /win32manifest:` で埋め込む。キャレット矩形は物理ピクセルで返るため、宣言しないと複数モニタ環境でバッジ位置がずれる。

**さらに、バッジフォームは `AutoScaleMode.None` とする。** PerMonitorV2 を宣言すると WinForms がフォームの `Size` と `Font` を DPI に応じて自動スケールし、物理ピクセル座標に対して二重にスケールが掛かるため。バッジは境界なし・`Size` 手動設定・`Location` 手動計算なので、自動スケールは不要である。

**未検証**: 開発機は 1920×1032 の 100% スケーリングのため、DPI 経路は一度も実行されていない。この項目は宣言を正しく行うことに留め、当該機での追加検証は行わない。

## 8. エラー処理

| 状況 | 挙動 |
|---|---|
| 昇格プロセス（UIPI） | 管理者権限アプリの情報は非昇格プロセスから読めない。何も表示しない。既知の制約として README に明記する。本体を昇格させれば回避できるが、常駐アプリとして割に合わないため採用しない。 |
| `SendMessageTimeout` タイムアウト（200ms） | 直前の値を保持。3 回連続で失敗したらバッジを隠す。 |
| MSAA / UIA が例外を送出 | 握りつぶして「キャレットなし」として扱う。 |
| `ImeDecoder` が未知のビット組合せを受領 | 例外を投げず、誤ったグリフも出さない。中立的な「IME ON」バッジ（表示文字「■」、色は緑）にフォールバックする。 |
| 多重起動 | 名前付き Mutex で防止。2 つ目のインスタンスは即座に終了する。 |

## 9. テスト方針

.NET Framework 単体では NuGet なしにテストフレームワークが使えないため、**`--self-test` 引数で内蔵アサーションを走らせる方式**を採用する（外部依存ゼロ）。

### 9.1 自動テスト対象（純粋関数のみ）

**`ImeDecoder`** — 以下を最低限のケースとする:

| 入力 | 期待 | 根拠 |
|---|---|---|
| `open=0`, `conv` 任意 (`0x0`/`0x9`/`0x19`) | `Off` | 実測 |
| `open=1, conv=0x9` | `Hiragana` | 実測 |
| `open=1, conv=0x3` | `HalfKatakana` | 実測 |
| `open=1, conv=0x8` | `FullAlnum` | 実測 |
| `open=1, conv=0xB` | `FullKatakana` | ビット定義からの推論 |
| `open=1, conv=0x0` | `HalfAlnum` | ビット定義からの推論 |
| `open=1, conv=0x19` | `Hiragana` | ROMAN ビットが無視されることの確認 |

**`BadgePlacer`** — 画面端での反転、マルチモニタ境界での基準モニタ選択。

**`BadgeStateMachine`** — 表示・非表示の全トリガーと競合解決。時刻は引数で受け取り、テストでは偽の時計を渡す。特に「フェード完了後に同じアプリ内で別の入力欄へ移動した場合も表示する」経路を必ずテストする。ここが抜けると、キャレットが一度も消えない移動でバッジが二度と出なくなる。

**`Settings`** — ini のパース、不正値の無視、`Opacity` のクランプ。

### 9.2 コンソール出力の扱い

`csc /target:winexe` でビルドした実行ファイルにはコンソールが接続されていないため、`Console.WriteLine` の出力はどこにも表示されない。テストが黙って通ったように見える事故を防ぐため、**`--self-test` 指定時は `AttachConsole(-1)` を呼んでから出力し、失敗件数をプロセス終了コードに設定する。**

### 9.3 手動確認（回帰手順）

Win32 依存部は自動テストできない。以下を回帰手順として維持する。

1. メモ帳、エクスプローラー（F2 名前変更などの Win32 `Edit`）、Edge、Chrome、VS Code、Cursor、Windows Terminal でそれぞれ入力欄にフォーカスし、バッジがキャレット横に出ることを確認
2. 各アプリで半角/全角キーを押し、バッジが再表示されモードが変わることを確認
3. 入力を開始し、バッジが消えることを確認
4. バッジが消えた後、同じウィンドウ内の別の入力欄をクリックし、バッジが再び出ることを確認（Edge のアドレスバー ↔ ページ内入力欄、VS Code のエディタ ↔ 検索ボックス）
5. デスクトップやボタンにフォーカスし、バッジが出ないことを確認
6. バッジ表示中も入力が中断されないこと（フォーカスが奪われないこと）を確認
7. 空のメモ帳 `Ctrl+F` 検索ボックスにフォーカスし、バッジが出て**表示時間いっぱい留まる**ことを確認する（Bugfix 2 の確認項目。組み立てた位置は要素矩形の揺れに追従して移動判定にかかってはならない）
8. Edge で Web ページ本体（入力欄ではない場所）をクリックし、**ページ全体の大きさのバッジが出ない**ことを確認する

## 10. 設定ファイル

exe と同じディレクトリに `settings.ini` を置く。.NET Framework は JSON パーサを標準で持たないため、依存を増やさない ini 形式とする。ファイルが無ければ既定値で動作する。

| キー | 既定値 | 意味 |
|---|---|---|
| `Opacity` | `0.88` | バッジの不透明度（0.1〜1.0） |
| `ShowDurationMs` | `800` | 表示時間 |
| `FadeDurationMs` | `200` | フェードアウト時間 |
| `CaretMoveThresholdPx` | `2` | 入力開始とみなすキャレット移動量 |
| `PollIntervalMs` | `120` | ポーリング間隔 |
| `OffsetX` / `OffsetY` | `6` / `-4` | キャレットからのバッジ位置オフセット |
| `FontSize` | `10` | バッジの文字サイズ |

トレイアイコンの右クリックメニューから「一時停止 / 再開」「設定ファイルを開く」「設定を再読み込み」「終了」を提供する。

## 11. スコープ外

- 昇格プロセス（管理者権限アプリ）への対応
- IME の状態を**変更**する機能（読み取り専用のツールとする）
- Microsoft IME 以外のサードパーティ IME に対する動作保証（IMM32 互換経路を持つものは動作する見込みだが検証しない）
- 変換候補ウィンドウの位置制御
